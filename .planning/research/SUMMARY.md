# Project Research Summary

**Project:** MoveKit (Windows C-drive cleanup tool using NTFS junctions)
**Domain:** Windows desktop application testing and quality assurance (greenfield-quality milestone)
**Researched:** 2026-06-21
**Confidence:** HIGH

## Executive Summary

MoveKit is a Windows desktop application (Wails v2.12 + Go 1.23.5 + React 19 + TypeScript) that migrates user folders off the C: drive using NTFS junction points -- a fundamentally destructive operation that demands rigorous testing. This milestone is a greenfield-quality iteration: no new features, just bug fixing and test coverage improvement targeting 80%+ Go coverage and CI automation.

The recommended approach, synthesized from four parallel research streams, follows a strict dependency order: fix the 8 known bugs first (with regression tests that prove the fix works), then establish CI/lint infrastructure so every subsequent change gets automated verification, then build Go backend test coverage from unit tests through integration tests, then add frontend component tests, and finally cap it with a smoke test. This order is non-negotiable because each phase unlocks the next -- you cannot write reliable backend tests without syscall interface abstraction, you cannot get meaningful integration tests without solid unit coverage, and you cannot run integration tests without a Windows CI pipeline.

The central risk is that MoveKit deep Win32 API integration makes naive testing destructive. Calling Rollback in a test without stubbing the registry will corrupt the developer actual user profile. Creating NTFS junctions without explicit cleanup in Cleanup will leak orphaned directories. Mocking Win32 syscalls at the DLL level will produce tests that pass but validate nothing real. All four research files converge on the same mitigation: inject thin Go interfaces at the business-logic boundary (not at the syscall layer), use real NTFS junctions in isolated TempDir directories for integration tests, and never touch real HKCU registry keys from tests.

## Key Findings

### Recommended Stack

The testing stack spans three domains: Go backend testing, React frontend testing, and CI/CD. All technology choices are version-verified and compatible with the existing codebase (Go 1.23.5, Wails v2.12, Vite 8, React 19).

**Core technologies:**
- **testify v1.11.1** -- Go assertions, suite orchestration, and mock framework. De facto standard (180K+ projects). Version pin avoids the Go 1.25+ requirement of testify/v2. HIGH confidence.
- **uber-go/mock v0.6.0** -- Interface-based code generation mocking. Official successor to archived golang/mock. Generates type-safe mocks from go:generate directives.
- **vitest v4.1.9** -- React component test runner with native Vite 8 integration. 10-20x faster startup than Jest. Drop-in Jest API compatibility.
- **@testing-library/react v16.3.2 + user-event v14.6.1** -- Industry-standard React component testing. Tests user-visible behavior, not implementation details. React 19 fully supported.
- **@playwright/test v1.61.0** -- End-to-end testing against wails dev at localhost:34115. For smoke tests on release validation, not per-commit CI.
- **GitHub Actions on windows-latest runner** -- Wails requires Windows for CGO + WebView2. Linux/macOS cross-compilation is not supported.

**Key architectural decision:** Win32 API abstraction via Go interfaces, not DLL mocking. Define interfaces for each capability group (JunctionAPI, FileOpsAPI, RegistryAPI, NotificationAPI, VolumeAPI). Concrete implementations in internal/syscall. Mocks generated by uber-go/mock. Inject into internal/migrate via constructors. This is MEDIUM confidence -- the pattern is established but specific interface boundaries need phase-specific design work.

### Architecture Approach

Five-layer test architecture, each layer building on the one below:

1. **L1: Go Unit Tests** -- Standard testing, table-driven, TempDir, MapFS. Pure Go logic. No external dependencies. Currently ~30% coverage.
2. **L2: Go App Layer Tests** -- testify/suite + uber-go/mock. Tests 17 Wails-bound methods with injected FolderReader, Migrator, EventEmitter interfaces.
3. **L3: React Component Tests** -- Vitest + RTL + jsdom. Tests 12 components. Mock Wails bindings via vi.mock(). Independent of Go backend.
4. **L4: Integration Tests** -- Go test binary, TempDir, real NTFS junctions. Full Migrate+Rollback pipeline. Windows-only.
5. **L5: End-to-End Tests** -- Playwright against wails dev. Smoke tests. Manual release validation.

**Five architectural patterns:** Interface Injection on App struct, Mock Wails Binding Proxy, Real NTFS Junction Integration Tests, Playwright E2E against dev server, StubRegistry for test isolation.

**Key dependency rule:** L1 first (no deps), then L2 (depends on L1), then L4 (depends on L2). L3 and L5 are independently buildable.

See: .planning/research/ARCHITECTURE.md for full system overview, data flow diagrams, anti-patterns, and suggested build order.

### Critical Pitfalls

Top 5 pitfalls ranked by severity and likelihood:

1. **Junction Test Leakage (P1)** -- os.RemoveAll cannot reliably delete NTFS junctions. Tests creating junctions in TempDir without explicit cleanup leak orphaned directories and cause cascading failures. **Prevent:** Always call DeleteJunction + os.Remove in Cleanup before TempDir cleanup. Keep junction targets inside same temp tree.

2. **Registry Pollution (P2)** -- Writing to real HKCU User Shell Folders during tests permanently breaks developer Desktop configuration. **Prevent:** RegistryAccessor interface with in-memory fake. Integration tests use dedicated test key path with go:build integration tag.

3. **Rollback Test Destruction (P5)** -- Calling Rollback in a test deletes real junctions, moves files, rewrites registry. Catastrophic. **Prevent:** Do not write rollback_test.go until registry+filesystem interface abstractions are complete. Add MOVEKIT_TEST_MODE env guard.

4. **Shared Cancelled Flag (P4)** -- Package-level atomic.Int32 in move.go makes parallel tests impossible. **Prevent:** Refactor moveFilesCrossVolume to accept context.Context. App struct holds its own CancelFunc.

5. **Wrong Mock Layer (P3)** -- Mocking Win32 syscalls at DLL level produces tests that validate assumptions, not real behavior. **Prevent:** Mock at business-logic layer. Test junction functions with real NTFS in TempDir.

Additional pitfalls: VFS library gaps (P6 -- afero lacks NTFS support), ACL permission cleanup (P7), error swallowing patterns (P8).

See: .planning/research/PITFALLS.md for full pitfall documentation including recovery strategies, warning signs, and the "Looks Done But Is Not" checklist.

## Implications for Roadmap

Based on combined research across all four files, the recommended phase structure follows a strict dependency order. Each phase unlocks the next.

### Phase 0: Bug Fix Foundation
**Rationale:** The 8 known bugs block meaningful test coverage. Writing tests against buggy code validates wrong behavior and creates technical debt. BUG-03/05/06/08 share root cause (error swallowing) -- fix as a group.

**Delivers:** 8 bug fixes, each with a regression test. Error handling audit completed. moveFilesCrossVolume refactored to context-based cancellation. All silent error swallows fixed.

**Addresses features:** T3 (Regression Tests), T5 (Error Handling Audit), partially T1

**Avoids pitfalls:** P4 (Shared cancelled flag), P8 (Error swallowing)

**Dependencies:** None -- starting point.

**Research needed:** MINIMAL. All 8 bugs documented in CONCERNS.md. Standard Go patterns apply.

### Phase 1: CI/CD Infrastructure
**Rationale:** Automated verification must exist before any new test code. Without CI, "works on my machine" is the only quality gate -- unacceptable for a data-moving tool.

**Delivers:** GitHub Actions on windows-latest. golangci-lint with .golangci.yml. wails build verification. go test -race. tsc --noEmit. Coverage reporting via gotestsum. All existing lint violations fixed.

**Addresses features:** T2 (CI/CD Pipeline), T4 (Static Analysis), T6 (Build Verification)

**Dependencies:** Phase 0 (bug fixes should pass before CI gates code)

**Research needed:** MINIMAL. Well-documented patterns.

### Phase 2: Go Backend Test Coverage
**Rationale:** Backend is the foundation. Migration logic, junction operations, registry handling, rollback. If backend has bugs, frontend testing is meaningless. This is the largest phase.

**Sub-phase 2a: Syscall Interface Abstraction**
Introduce interfaces for JunctionAPI, FileOpsAPI, RegistryAPI, NotificationAPI, VolumeAPI. Concrete impl in internal/syscall. Mocks via uber-go/mock. Create internal/testutil/ with StubRegistry, CreateTempTree, MockEventEmitter.

**Sub-phase 2b: Unit Test Writing**
Write _test.go for all uncovered files. Target 80%+ with CI coverage gate. Audit test isolation.

**Sub-phase 2c: Migration Scenario Fixtures**
Create fixture functions for common scenarios (OneDrive KFM enabled, Google Drive syncing Desktop, low battery laptop).

**Delivers:** 80%+ Go coverage. RegistryAccessor interface with in-memory fake. Syscall interfaces for all Win32 boundaries. Coverage enforcement CI gate. Fixture library.

**Addresses features:** T1, D3, D4, D5, T8

**Avoids pitfalls:** P1, P2, P3, P5, P6, P7

**Dependencies:** Phase 1 (CI), Phase 0 (bug-free code). 2a must complete before 2b for 5-7 files.

**Research needed:** SIGNIFICANT for Sub-phase 2a. Win32 interface boundaries need phase-specific design. process.go and shell.go test strategies unclear. Allocate research-phase task during Phase 2 planning.

### Phase 3: Frontend Quality
**Rationale:** Independent of Go backend -- can overlap Phase 2 if resources allow. TypeScript strict mode first catches bugs test setup would mask.

**Sub-phase 3a: TypeScript Strict Mode** -- strict: true, fix errors.
**Sub-phase 3b: Component Test Infrastructure** -- Vitest + jsdom + global setup + Wails mock factory.
**Sub-phase 3c: Component Tests** -- 12 React component test files.

**Delivers:** TypeScript strict mode enabled. Vitest + RTL infrastructure. 12 component test files. Wails mock factory. Prettier + ESLint.

**Addresses features:** D1, D6, T7

**Dependencies:** Phase 1 (CI). Independent of Phases 0/2.

**Research needed:** MEDIUM. Wails runtime mocking strategy needs validation via spike test.

### Phase 4: Integration Verification
**Rationale:** Capstone. Validates Phases 0-3 produced a working whole.

**Sub-phase 4a: Go Integration Tests** -- Full Migrate+Rollback roundtrip with real NTFS junctions.
**Sub-phase 4b: Binding Integration Tests** -- Test Wails bridge between Go and JS.
**Sub-phase 4c: Smoke Test** -- Full user journey via Playwright.

**Delivers:** Full Migrate+Rollback integration test. App.StartMigration integration test. Binding correctness tests. Smoke test.

**Addresses features:** D2, D7

**Dependencies:** Phase 2 (backend must be reliable). Phase 3 (UI stable for smoke test).

**Research needed:** MEDIUM. Wails binding test harness sparsely documented. CI runner WebView2 verification needed.

### Phase Ordering Rationale

1. **Bug fixes before tests (Phase 0 before 2-4)** -- Tests validating buggy code are technical debt (PITFALLS.md P8).
2. **CI before test writing (Phase 1 before 2-3)** -- Every test should be verified by CI immediately. Wails build verification catches unique embed/link errors.
3. **Syscall abstraction before coverage (Phase 2a before 2b)** -- 5-7 Go files untestable without interfaces (ARCHITECTURE.md boundaries).
4. **Backend before frontend integration (Phase 2 before 4)** -- Flaky integration tests waste more time than no tests (FEATURES.md dependency graph).
5. **Frontend can parallelize (Phase 3 overlaps 2)** -- Different language, tools, environment. Resource allocation determines overlap (ARCHITECTURE.md L3 independence).
