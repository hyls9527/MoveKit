# Stack Research — Testing & QA

**Domain:** Windows desktop application testing (Go 1.23.5 + Wails v2.12 + React 19 + TypeScript)
**Researched:** 2026-06-21
**Confidence:** HIGH

### Win32 API Mocking Strategy (Architectural Pattern, Not a Library)

MoveKit's `internal/syscall` package currently calls `syscall.NewLazyDLL("kernel32.dll")` directly at package level (`var` blocks). This makes unit testing impossible without real Windows kernel. The tested approach is:

1. **Define interfaces** for each Win32 capability group:
   - `JunctionAPI` — `CreateJunction`, `IsJunction`, `DeleteJunction`
   - `FileOpsAPI` — `MoveFileEx`, `CopyFileEx`, `GetDiskFreeSpaceEx`
   - `RegistryAPI` — `ReadExpandString`, `WriteExpandString`
   - `NotificationAPI` — `SHChangeNotify`
   - `VolumeAPI` — `GetVolumeInformation`

2. **Concrete implementation** lives in `internal/syscall` as today, implementing the interfaces.

3. **Dependency injection** — `internal/migrate` packages receive API interfaces via constructor or struct fields (Go's implicit interface satisfaction).

4. **Test mocks** generated by `go.uber.org/mock/mockgen` from interface definitions using `//go:generate mockgen -destination=mocks/xxx_mock.go -package=mocks github.com/movekit/movekit/internal/syscall JunctionAPI`

5. **In tests**, inject mocks that return controlled results — e.g., mock `IsJunction` to return `true`/`false` to test different code paths without touching real NTFS.

This is a MEDIUM confidence recommendation — the abstraction pattern is well-established in Go, but the specific interface boundaries for MoveKit's Win32 calls need phase-specific design work. See PITFALLS.md for details.

### Wails Runtime Mocking (Frontend)

Frontend components import from `../../wailsjs/go/main/App` (auto-generated bindings) and `../../wailsjs/runtime/runtime`. To test components in isolation:

| Strategy | Tool | How |
|----------|------|-----|
| Module-level mocking | `vi.mock()` | `vi.mock('../../wailsjs/go/main/App', () => ({ GetFolders: vi.fn().mockResolvedValue(mockFolders), ... }))` |
| Global window stub | Setup file or `vi.stubGlobal()` | `window['go'] = { main: { App: { GetFolders: vi.fn(), ... } } }` and `window.runtime = { EventsOn: vi.fn(), EventsEmit: vi.fn(), ... }` |
| Shared mock factory | `src/test/mocks/wails.ts` | Reusable mock file exporting a `setupWailsMocks()` function that stubs all bindings with sensible defaults |

Recommended: **Shared mock factory** pattern. Create `frontend/src/test/mocks/wails.ts` with a factory function that produces mock implementations for every binding method and runtime function. Each test imports and configures only what it needs. This follows the pattern documented in the Wails community (RdHamilton/MTGA-Companion#470).

## Alternatives Considered

| Recommended | Alternative | Why Not |
|-------------|-------------|---------|
| `stretchr/testify` v1.11.1 | `go-openapi/testify/v2` | Requires Go 1.25+; MoveKit is on 1.23.5 |
| `stretchr/testify` v1.11.1 | `go-tests/assert` (stdlib-style) | No `assert`/`require` distinction; less ergonomic for exhaustive checks |
| `uber-go/mock` v0.6.0 | `vektra/mockery` v2 | mockery is heavier (CLI-based, config file required); gomock's `//go:generate` pattern fits existing codebase better |
| `vitest` v4.1.9 | `jest` v30 | Jest is slower (CJS overhead), requires `ts-jest` or `@swc/jest`, and doesn't share config with Vite 8. The project already uses Vite — using Vitest is zero-config |
| `vitest` v4.1.9 | `bun test` | Bun runtime; MoveKit frontend is Node.js-based; switching runtimes adds complexity |
| `@testing-library/react` v16.3.2 | `enzyme` | Enzyme is unmaintained since React 18; does not support React 19 |
| `@playwright/test` v1.61.0 | `cypress` | Cypress cannot communicate with Go backend directly; Playwright has better Wails community adoption and test patterns |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| `golang/mock` (original Google repo) | Archived since 2023, no Go version updates. Does not support generics | `uber-go/mock` v0.6.0 |
| `stretchr/testify/mock` | While bundled with testify, `uber-go/mock` generates far less boilerplate and provides compile-time type safety | `uber-go/mock` + testify assertions |
| `jest` | CJS-first, slow startup, separate config from Vite. Config drift between dev and test environments | `vitest` v4.1.9 |
| `enzyme` | Abandoned since React 18; no React 19 support | `@testing-library/react` v16.3.2 |
| `fireEvent` (from @testing-library/react) | Direct DOM event dispatch — doesn't simulate real user behavior (misses intermediate events like `focus` before `click`) | `@testing-library/user-event` (e.g. `await user.click()`) |
| `jsdom` from `vitest` built-in (via `environment: 'jsdom'`) | Vitest includes a bundled jsdom, but explicit `jsdom` npm dep ensures version control and avoids bundler version drift | `jsdom` v26.0.0 as explicit devDependency |
| Cross-platform CI (`ubuntu-latest`) | Wails requires Windows for CGO + WebView2; Linux builds fail at link stage | `windows-latest` GitHub Actions runner |
| CI without `wails build` | Running only `go test` misses build/embed/link errors unique to Wails' WebView2 integration | Always include a `wails build` step in CI |

## CI Pipeline Pattern

```yaml
# .github/workflows/test.yml
name: Test & QA
on: [push, pull_request]

jobs:
  test:
    runs-on: windows-latest  # Wails requires Windows
    steps:
      - uses: actions/checkout@v4

      # Go
      - uses: actions/setup-go@v5
        with: { go-version: '1.23.5' }
      - run: go mod download

      # Frontend
      - uses: actions/setup-node@v4
        with: { node-version: '22' }
      - run: cd frontend && npm ci

      # Build (catches embed/link errors)
      - run: wails build

      # Lint
      - run: golangci-lint run ./...
      - run: cd frontend && npx tsc --noEmit

      # Unit Tests
      - run: gotestsum --junitfile report.xml -- -race -coverprofile=coverage.out ./...
      - run: cd frontend && npx vitest run --coverage

      # E2E (requires wails dev in background)
      - run: wails dev &
      - run: cd frontend && npx playwright test

      # Coverage gate
      - run: go tool cover -func=coverage.out | grep total
```

**CI cost note:** `windows-latest` runners consume 2x GitHub Actions minutes vs Linux. This is unavoidable for Wails. Mitigate by:
- Caching Go modules (`actions/cache@v4`)
- Caching npm dependencies (`actions/cache@v4`)
- Running E2E tests only on `main` branch merges (not every PR commit)
