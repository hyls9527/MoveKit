<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub push event -> CI runner | Untrusted code (from any branch) executes on CI runner |
| CI runner -> GitHub Releases API | Release job has `contents: write` permission to create releases |
| CI runner -> npm registry | `npm ci` downloads packages; integrity verified by lockfile hash |
| CI runner -> Go module proxy | `go install` downloads tools (golangci-lint, gotestsum, wails CLI) |
| Dependabot -> repository | Dependabot opens PRs with dependency updates |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | Third-party GitHub Actions (setup-go@v5, setup-node@v4, checkout@v4, cache@v4, upload-artifact@v4, golangci-lint-action@v7, softprops/action-gh-release@v2) | mitigate | All actions are major-version pinned. Dependabot configured for github-actions ecosystem keeps them current. All are official GitHub or well-maintained community actions with millions of users. |
| T-02-02 | Information Disclosure | PR from fork — secrets exfiltration via workflow modification | mitigate | Workflow-level `permissions: contents: read`. Only the release job (which runs exclusively on tag push, not PR) has `contents: write`. Fork PRs get read-only GITHUB_TOKEN automatically. |
| T-02-03 | Tampering | Go tool installation (`go install golangci-lint@v2.11.3`, `gotestsum@v1.13.0`, `wails@v2.12.0`) | mitigate | All versions pinned to exact tags. Go module proxy verifies checksums against `sum.golang.org`. Wails CLI installation uses the official module path `github.com/wailsapp/wails/v2/cmd/wails`. |
| T-02-04 | Tampering | `npm ci` dependency installation | mitigate | `npm ci` uses lockfile integrity hashes (NOT `npm install`). Every package in lockfile has a verified integrity hash. If lockfile is tampered with, `npm ci` fails. |
| T-02-05 | Elevation of Privilege | Release job with `contents: write` | mitigate | Release job is condition-gated on `startsWith(github.ref, 'refs/tags/v')`. Only users with tag push permission can trigger it. Tag creation requires write access to the repository. |
| T-02-06 | Denial of Service | CI runner resource exhaustion (infinite loops, hung processes) | mitigate | Every job has `timeout-minutes: 15` (per D-16). Concurrency cancellation (per D-02) stops stale runs when new commits push. GitHub Actions has per-account minute quotas as a backstop. |
| T-02-07 | Tampering | Cache poisoning via malicious PR modifying lockfiles | mitigate | Cache keys include `hashFiles('go.sum')` and `hashFiles('frontend/package-lock.json')`. Different lockfile content produces different cache keys. PR caches are scoped to the PR branch. |
| T-02-08 | Repudiation | Release created without audit trail | accept | GitHub Releases are immutable once published (can be deleted but deletion is logged). The release is tied to a specific commit SHA. Release notes are auto-generated from commit history. Low risk given project scope. |
</threat_model>
